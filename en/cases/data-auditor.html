Case study

Cotejo / Data Auditor

The problem. A high comparison score can coexist with low matching coverage.

My role. I conceived, designed and developed this personal support tool, which I use myself.

Approach. Declare key columns, fields and comparison settings.

  • JavaScript
  • Python
  • DuckDB

Context

Comparing extracts field by field needs a clear scope: keys, evaluated fields, source formats and normalization rules. The tool supports investigating differences; source-data owners retain business acceptance.

Approach

  1. Declare key columns, fields and comparison settings.
  2. Select the browser JavaScript or desktop Python / DuckDB engine.
  3. Compare matched rows and report orphan rows separately.
  4. Review differences, control totals and matching coverage before interpreting a score.

What this work produced

The result is a personal local comparison tool that separates field agreement from matching coverage. It supports investigation rather than approving a business process on its owner’s behalf.

Technical detail

The score concerns matched rows and evaluated fields; orphan rows are separate. No shared keys means there is no basis for a score. A missing required key column is a configuration error, a different situation from valid inputs with no matching keys.

Engineering considerations

Browser and desktop engines differ in their treatment of surrounding tabs and line breaks. Their behavior must be checked for the intended inputs. Formats, tolerances and pairing rules change the comparison question; similar implementations do not guarantee equivalent results.
